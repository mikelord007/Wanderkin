## What was asked

Make fabric/wood/metal surfaces meaningfully distinct and more believable, and lighting that
sells miniature scale — on the real production scene, not a proposal/demo. Explicitly required:
inspect actual mesh/material/UV structure before assigning any material identity; prefer
explicit known-sample mapping or deterministic evidence; neutral fallback for unknown combined
meshes; never label an arbitrary whole mixed mesh as one material.

## What the mesh/asset pipeline actually is (evidence, not assumption)

Parsed the JSON chunk of every `.glb` shipped or generated by this project
(`public/samples/rodin.glb`, `public/samples/tripo.glb`, and the 3 files under `storage/assets/`
at the time of this work): **every one is exactly one mesh with exactly one material.** The
material shape is identical across all of them — `pbrMetallicRoughness.baseColorFactor` is
`[0,0,0,1]` (black), `metallicFactor: 0`, and all visible colour lives in a single
`emissiveTexture` (a baked "shaded" atlas, the classic AI-photogrammetry unlit-bake output).
There is no per-submesh material, no `Wood_Mat`/`Fabric_Mat`/`Metal_Mat` naming, and — extracted
and visually inspected the actual baked PNG atlas from `rodin.glb` — the UV layout is a
scrambled photogrammetry chart-pack (small disconnected triangle-island crops with no spatial
organisation), not a hand-painted texture a UV mask could reliably target.

Consequence: **UV-space region masking is not feasible on these assets, and no per-submesh
material data exists to read.** Any material differentiation had to come from either (a) a
structural property of the material itself (safe, applies to everything), or (b) an explicit,
already-measured world-space region on a specific known asset (safe only for that one exact
asset, by content hash).

## Part 1 — universal fix: real lighting response (all generated meshes, every level)

Root cause of "flat, sticker-like" furniture: `baseColorFactor` black + `emissiveTexture` means
the object is **fully self-lit and ignores the scene's lights entirely** — the previous style
shader only post-processed colour (saturation/contrast/outline/paper grain) after this already-lit
value, so no key/fill/ambient light direction, distance, or shape ever showed on any generated
object, regardless of `SceneLighting`'s tuning.

`src/scene/styleMaterial.ts` now detects this exact structural shape —
`isBakedEmissiveOnlyMaterial()`: `MeshStandardMaterial`, no `map`, has `emissiveMap`, black
`color`, `metalness < 0.05` — and rewires it (`relightBakedEmissiveMaterial()`): the baked
texture moves from `emissiveMap` into `map`, `color` resets to white, `emissive` resets to
black. Standard PBR shading (ambient + hemisphere + directional N·L) now modulates that same
preserved texture, using the exact `StyleLighting` intensities already tuned for the floor/step
helper materials — no new exposure multiplier, so this does not double up brightness, it makes
the already-tuned lighting visible on these surfaces for the first time.

This is a **structural** check, not a semantic one: a material with a real base-colour map, or a
deliberately emissive decorative object (non-black base colour), never matches and is left
completely untouched. Applies identically to the Rodin sample, the Tripo sample, and every
user-generated asset — verified in-browser on both bundled samples (see evidence below); no
region/bump treatment is implied or required for this part.

Honest limitation: the source texture's own baked lighting from the original photos cannot be
removed by this or any texture-preserving transform — an object photographed lit from one side
will still look faintly lit from that side. This makes the object responsive to the scene's
lighting again; it does not reconstruct a true lighting-free albedo from a single baked capture.

## Part 2 — known-sample-only: wood/fabric region detail

Scope: **only** `public/samples/rodin.glb` ("The desk & sofa adventure"), matched by its actual
decoded content hash (`c750cb2c1fcd2197f8c373b791703bc90073075e11d08cafb0be4d84012d54b8`, the
same value already declared in `src/scene/samples.ts`'s manifest and independently re-verified
by loading the file), in new `src/scene/materialRegions.ts`. The Tripo sample and every
user-generated asset get **only** Part 1 (safe, texture-preserving, uniformly lit) — no fabric/
wood split is applied or claimed for them.

The region boundary is not a visual guess: it reuses the desk's own already-measured, already-
documented standable-surface bounding box from `src/scene/samples.ts` (`RODIN_DESK_Y`, "spans
world x −0.06…3.18"), produced independently by `analyze-sample.ts` from the real geometry. The
sofa occupies the rest of the same combined mesh on the −X side (spawn and checkpoint 0 both sit
at x=−4.02, documented "beside the sofa end"). A single world-space X divider at that boundary,
with a 0.4 m smoothstep blend, splits the one mesh into a "wood" side (x ≥ −0.06) and a "fabric"
side — anchored to the object in world space (via a `modelMatrix * position` vertex varying), so
it does not depend on the UV atlas at all and doesn't swim with the camera.

**No metal region is applied.** There is no measured or documented evidence of a distinct metal
part on this asset (no bounding box, no separate material, nothing observed in the extracted
texture atlas) — adding one would have been exactly the "arbitrary label on a mixed mesh" this
task explicitly said not to do, so it was left out rather than guessed.

Per-region detail (fragment shader, `src/scene/styleMaterial.ts`):
- **Roughness**: wood ≈0.42–0.62 (semi-matte), fabric ≈0.55–0.97 (matte, restrained noise
  variation), smoothly blended across the divider.
- **Normal bump**: wood gets low-frequency ring/fiber grain along the desk's long axis; fabric
  gets an isotropic woven-cushion bump. Applied via the surface-gradient method (Mikkelsen,
  "Bump Mapping Unparametrized Surfaces on the GPU") from screen-space derivatives of true
  view-space position and a scalar height field — this works on curved, arbitrarily-oriented
  surfaces (the sofa's cushions/legs), not just a flat upward-facing desktop.
- No new texture assets: both are pure code-native procedural GLSL (value noise + `sin`), no
  downloaded/generated/paid texture dependency.

### A real bug found and fixed during this work (not shipped)

The first working version of the normal-bump math produced severe, ugly diagonal light/dark
banding across the desktop, reproduced at close range (not a distance/aliasing effect — ruled
out by testing with the bump disabled at the identical camera position, and separately by
lowering noise frequency, before finding the real cause). Root cause, found by bisection: the
Mikkelsen formula's `det` term can be small or cross zero on this mesh (a single AI
reconstruction with no guaranteed consistent triangle winding), and the initial implementation
divided by `abs(det)`, which explodes near a zero crossing and silently drops the correct sign
when `det` is negative. Fixed to the textbook non-dividing form (`normalize(abs(det)*N −
sign(det)*gradient)`), which stays bounded everywhere; separately simplified the wood height
field's most anisotropic term (previously stretched 45× between its two axes, which is
independently a bad case for hardware screen-space derivatives) to an isotropic, lower-frequency
one. Both fixes verified by re-rendering the exact same on-desk camera position (see evidence).
A conservative `oqDetailFade()` (compares noise frequency against `fwidth` of world position) is
also in place to fade the detail out before it could under-sample at real distance/grazing
angles, independent of the bug above.

## Part 3 — lighting (`src/game/render/SceneLighting.tsx`)

- **Warmer, lower "window" key light**: the authored `keyPosition` per style is a steep,
  near-overhead sun angle. Only the *elevation* is lowered here (a local scene-graph placement
  choice, not a `shared/style.ts` data change) — the per-style horizontal direction and every
  `StyleLighting` intensity/colour/softness value are read unchanged, so all three styles keep
  their own mood. A lower, more raking angle reads as "small object lit through a room window"
  and produces longer, more legible contact shadows — the depth cue tilt-shift/miniature
  photography relies on.
- **Hemisphere ground-colour fix**: `style.sceneColors.surfaces[3]` (an outdoor grass-green
  swatch) was reused as the hemisphere light's "ground" bounce term. That was invisible before
  (baked materials ignored all lighting), but once real relighting was in place it made every
  downward-facing furniture surface (a desk's underside, a sofa's frame) pick up a
  thematically-wrong green tint as its only upward fill. Blended 55% toward the warm fill colour
  instead — floor lighting (which faces the sky) is unaffected; only surfaces facing away from
  it change. This was found and fixed by direct observation (see before/after evidence) — it is
  the specific mechanism behind "readability beneath furniture."
- **Shadow map resolution doubled** (1024→2048) on the single shadow-casting key light only (the
  fill light never casts) — crisper contact shadows under furniture at a fixed, small, one-light
  cost; no new shadow pass, no global post-effect.
- Fill light gets a soft warm bounce-tint (blended 22% toward the key colour) standing in for a
  window key's bounce off nearby surfaces; there is no environment map/IBL in this renderer, so
  the existing hemisphere term remains the sky/ground fill.

Reduced-motion/particles: untouched — no new particles or ambient-motion elements were added by
this work.

## What was not done / residual limitations (stated honestly)

- **Hand-painted and watercolor styles were not visually verified in-browser.** The bundled
  "Play now" sample flow always plays the default (Cartoon) style; there is no in-flow style
  switch for it. The region/relight code does not branch on `style.id` at all (it composes with
  whichever style-specific fragment is already selected), so there is no logical reason it would
  behave differently, and this was confirmed by unit test (materials construct successfully and
  tag distinct cache keys for all three `STYLE_DEFINITIONS`) — but that is not the same as a
  pixel-verified render. Flagging for follow-up if the coordinator wants that closed.
- **No metal treatment anywhere.** Explicitly not attempted without evidence, per the task's own
  instruction — see Part 2.
- The Tripo sample and all user-generated/storage assets get Part 1 (relight) only, never a
  region split — this is the "neutral fallback for unknown combined meshes" the task asked for,
  not a shortcut; extending real region detail to a new asset would need the same kind of
  measured, documented bounding-box evidence this one had, which does not exist for those.
- Lighting tuning (window elevation ratio, hemisphere blend %, bounce-tint %) was iterated by
  actual visual inspection of the real scene, not derived analytically — the numbers in
  `SceneLighting.tsx` are the result of that process, documented inline with the reasoning.
- Did not re-run the full `tests/e2e/browser` acceptance suite — scope was a focused, verified
  slice per the assignment; the coordinator/user can request it once source freezes across all
  three concurrent workers.
